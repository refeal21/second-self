# 售前 PPT 技能、多页生成与版本审核设计

日期：2026-09-09

状态：用户已确认功能方向；本书面设计待审核，尚未实施。本文不代表现有应用已具备这些能力。

## 1. 目标与边界

让工作台制作适用于 ToB / ToG 的建设方案售前 PPT：有明确的建设目标、相互对应的业务模块，以及由人物和业务流程讲清楚的使用场景，而不是把长文缩小字号堆在页面里。用户一次启动多页生成，可以在其他页面生成时查看、审核和修改已有页面，也能从历史版本提出修改意见。

保留本地 Tauri 2 / React / Rust / TypeScript Worker / SQLite 架构和 Codex App Server 的 ChatGPT 登录路径。不增加按量计费 API、API Key 配置、本地 HTTP 服务或新的渲染平台。不安装未经审查的第三方全局技能，不修改用户的 Codex 个人设置。模型可用性和限流仍由当前账号及服务决定，并发不承诺固定提速比例。

本次覆盖：售前规划和逐页设计规则接入真实提示词、持久任务队列、多页画廊、逐页审核、历史版本反馈、旧内容的显式修订副本、单页参考图绑定。模板颜色沿用已有项目配色能力；把图片真正套入 PPTX 母版及占位符仍属于独立的[模板套版设计](2026-09-08-template-image-export-design.md)，不能以“已应用模板配色”宣称已实现套版。

## 2. 已核实的问题

- 当前细化提示词规定 JSON 结构、内容来源和完整页面，但没有售前叙事、模块对应、场景脚本或信息密度设计规则。
- 当前图片提示词要求逐字保留已批准正文。这是内容保真约束；如果细化阶段批准的是长段落，出图阶段不能偷偷删减来换取美观。
- 当前页面选择、生成资格和审核推进共同依赖 `currentSlideId`；前端任务注册表也按项目互斥，因此不能直接把生成按钮改成 `Promise.all`。
- 当前图片请求绑定启动时的项目全局 revision；另一页提交结果或批准后会使它过期。图片结果尚无完整的持久暂存和仅重试提交机制。
- 当前图片历史已保留部分版本，但 UI 没有完整的多页历史查看和基于指定历史图修改的交互。现有短期图片会话使用 `ephemeral`，重启恢复不能假定服务支持找回。

## 3. 产品主流程

材料与项目说明 → 售前结构规划 → 整份大纲审核 → 全部页面细化与设计审核 → 一键多页生成 → 逐页看图、修改、批准 → 全部有效版本批准后转换与 QA。

大纲与细化仍必须整体批准。改变的是图片阶段：页面可以独立生成和审核，不必先批准第 N 页才能生成第 N+1 页。不得自动批准图片，也不得以任意历史批准代替当前交付版本的批准。

### 3.1 售前页面类型与内容约束

| 页面类型 | 必须讲清楚的内容 | 优先视觉表达 | 与后文的对应 |
| --- | --- | --- | --- |
| 建设目标 | 已知问题、期望改善、建设方向；没有依据的指标标为待确认 | 目标主图、前后对比、目标与能力关系 | 目标关联已确认模块，不虚构效果数值 |
| 架构图 | 层级、边界、真实系统关系；业务层展示后续模块 | 分层架构与有依据的连线 | 业务层模块与功能页使用同一份模块目录 |
| 总览 | 本方案模块的集合及各自定位 | 总览地图或有主次的模块关系图 | 默认替代架构页；用户明确需要时两者才并存 |
| 功能模块 | 需求、功能分类、场景，或把功能直接放入场景 | 主场景图配关键功能说明；分类关系适合时才用卡片 | 页面绑定模块，可一模块多页，也可明确标记多模块联动 |
| 场景流程 | 谁在什么场景下做什么，系统如何响应，下一角色如何接手 | 带人物、场所和清晰连接的流程图或分镜 | 每个步骤关联已经确认的功能；不能凭排版需要新增接口 |

共通规则：每页先确定一个核心信息，再选表达形式；页面正文与演讲备注分离；标题、重点、辅助说明有层级。信息过多时先提出拆页或压缩草稿，让用户在细化阶段批准，不能靠缩小字号或在出图时删字解决。图文并茂不等于每页加装饰照片；架构页的主要图形就是架构，场景页的主要图形是人物与流程。

架构、总览、功能和场景页共享稳定的 `moduleId`。校验模块遗漏、命名漂移、重复计数、无来源的关系；无法映射的内容进入可见的待确认项，不自动补造功能。模块目录是用户认可的售前表达，不把它冒充原始材料里的事实。

### 3.2 审核视图与技能元数据

大纲审核显示页码、标题、页面类型、核心信息、模块归属和来源。逐页细化显示最终上屏文字、备注、布局意图、视觉主体、模块映射及场景脚本，支持既有增删改查和排序。场景脚本包含角色、地点、触发事件、步骤、人物动作、系统响应、结果和功能关联。

场景人物动作、节点文字、系统响应等只要会影响页面内容，就属于需要用户审核的内容，不能在冻结后以“设计说明”名义偷偷添加。纯字号、间距和装饰布局可以作为视觉调整，但不能改变已批准的语义。

沿用严格 `SlideSpec` 字段，不把新字段随意塞入现有 JSON。新增版本化响应 envelope：大纲响应包含原有大纲对象与 `PresalesPlan`，细化响应包含原有 `SlideSpec[]` 与 `SlideDesignPlan[]`。分别校验后共同保存，任一部分不合法就整份不发布；不能仅解析成功的半份进入审核。旧项目没有这些伴随对象时按旧契约读取，不伪造已应用技能。

`PresalesPlan` 和 `SlideDesignPlan` 采用 Rust 监管的伴随存储，绑定 analysis、outline、spec 的版本和哈希。审批同时绑定内容与设计计划的哈希。改变任何将用于生成的上屏内容、场景语义或模块关系，都会使对应草稿的审批失效；冻结版本保持不变。

所有最终上屏文字只有一份权威：`SlideSpec` 的标题、正文、表格、图表或基础形状文字。场景节点和人物说明也须在这些字段中有确定位置，设计计划按稳定对象 ID 引用，不再独立复制另一套文字；`imageGenerationBrief` 仅描述表达方式，不能作为额外文案入口。演讲备注保存在设计计划中，明确不渲染到 PNG。图片提示词只取已批准的上屏对象与布局，不把备注或来源分析长文当作正文。

标题及 `body:string[]` 原本没有对象 ID，稳定 ID 存在伴随映射中，绑定冻结规格路径与文字哈希，而不是给严格 `SlideSpec` 增加未知字段。编辑器通过稳定 ID 更新草稿映射；数组排序后重新校验路径，不以旧数组下标猜测对象身份。

伴随设计计划与当前页面 ID 精确一一对应，所有模块和场景功能引用必须能在同版本规划中解析。手工增删页面、改正文、排序时，内容和设计计划以同一 revision 联合提交；删除页面同时删除它的设计草稿，新增页要补齐设计计划，排序保留稳定 ID。文字改动使映射失效时显示待修复对象，完成重新映射前不能批准，不允许只保存内容一侧形成悬空引用。

### 3.3 开源技能的取舍与真实接入

不是安装一个技能名称就完成接入。将经过审查的局部规则整理为工作台专用、随应用发布的售前技能包，固定版本、内容哈希、来源及许可证；不在运行时拉取 GitHub 最新文件。

| 参考来源及固定版本 | 使用范围 | 不直接采用 |
| --- | --- | --- |
| [PPT Master](https://github.com/hugohe3/ppt-master/tree/78fa4eebf67d38f33c51ec457c911d7e05013587/skills/ppt-master)，MIT | 关系优先的架构规划、整份叙事、场景化流程、图片与版式关系 | 不整体迁移 SVG / 原生 PPTX 工具链，不接收费图片接口 |
| [slides_maker](https://github.com/addsumtech/slides_maker/tree/02ea841a6283f3c262f0ff534d28091a3d9554e1/skills/slide-maker)，MIT | 根据信息关系选择页面形式、内容密度、独立质量复核 | 不把庞大的完整技能注入每页，不强制换成其 DeckKit 流程 |
| [baoyu-infographic](https://github.com/JimLiu/baoyu-skills/tree/6b7a2e417500561a5ecdd0b168332f4142584617/skills/baoyu-infographic)，MIT | 流程与分镜布局、场景图组织、参考图用途区分 | 不使用默认手绘或卡通风格覆盖企业模板，不额外接 API |

上述选择基于源文件与许可证检查，尚未以本项目三类样页验证最终视觉质量。实际复用文字、代码或资产时保留相应版权和许可，在第三方说明中逐项登记；自定义跨页模块映射不能声称是上游已经保证的能力。

实际请求路径：大纲 builder 注入整份售前规划规则；细化 builder 注入页面类型与场景设计规则；图片 builder 注入已批准的页面设计、项目模板配色及本页参考图用途。前端预览与发送使用同一构建器，防止预览正确但真正调用未带规则。

每次请求记录技能版本/哈希、实际提示词、内容与设计计划版本/哈希、配色版本、参考图版本和用户意见。只保存该项目实际使用的技能快照，按既有路径边界写入 `outline/presales/` 和 `slide-specs/presales/`；不向客户材料目录加入可执行脚本。技能文本作为指令，材料、用户附件与场景数据作为明确分隔的数据输入。

模板配色是颜色基准：不再默认为科技蓝。冲突的临时颜色意见提示用户通过项目配色修订处理；单页反馈不能悄悄覆盖全局已锁定模板规则。

## 4. 多页生成与查看

### 4.1 入口和默认行为

进入图片审核后显示全部页面缩略图和页码/标题。左侧选择页面，中间查看当前图及历史版本，右侧展示该页生成与审核状态。选中页只是查看状态，不决定后端能否生成其他页。

主按钮为“生成所有待生成页（N 页）”，默认只处理没有候选图、没有有效批准且没有未终结任务的页面，不重生成已经有图的页面。首次发起批次时显示范围和使用 Codex 账号额度的提示。另提供选择多页、重试失败页、暂停队列；批量替换已有候选图需要明确确认。

默认全应用最多同时执行 2 个图片任务，不是每项目各 2 个。同一页最多一个未终结生成请求，重复点击返回同一任务。队列遵循先入先出；不允许新项目无限越过旧任务。并发不包含本地短提交锁的占用时间。若服务只支持单任务或发生限流，显示原因并降为 1 或暂停；不切换模型计费渠道。

可以边生成边审核已完成的其他页。某页正在生成时，只禁用该页冲突操作；不锁住其他页面的查看、反馈和审核。全局配色、冻结内容或来源修订必须先处理相关任务，再进入修订流程。

### 4.2 状态和交互矩阵

| 状态 | 页面展示 | 用户操作与结果 |
| --- | --- | --- |
| 无图 | 页面设计摘要、“待生成” | 单页生成或纳入批量 |
| 排队 | 队列位置、等待原因 | 查看内容、取消尚未派发的任务 |
| 生成中 | 真实阶段与已用时间，不编造进度百分比 | 离页后继续；可申请停止本页，不能重复生成 |
| 已返回、保存中 | “图片已返回，正在保存” | 保存冲突仅重试本地提交，不重新出图 |
| 待审核 | 完整 PNG、生成依据 | 放大查看、填写意见生成新版本、人工核对后批准 |
| 已批准 | 当前交付版本标记 | 查看历史；显式创建修改分支，不覆盖旧批准 |
| 明确失败 | 错误、失败阶段、是否已获得图片 | 修复前置条件后明确重试；其他页不受影响 |
| 状态待确认 | 说明请求可能已送达，结果尚不确定 | 核查已有会话/结果；不自动重发，不显示“已取消” |
| 旧图缺失 | 缺失说明及可用元数据 | 不能批准或称已预览；选择其他有效版本或生成新候选 |

“暂停队列”只停止启动后续任务，已运行任务继续；“取消排队任务”不发送模型请求；“停止正在生成的任务”是取消申请，收到明确终态才释放槽位。未知结果与取消未确认仍占逻辑槽位，避免无意超并发。

例外只允许用户明确选择“放弃等待并重试”：提示原请求可能继续及重复消耗额度，确认后旧 attempt 转为本地 `abandoned_unresolved`，解除本地槽位/同页互斥，但保留远端结果未知标记和迟到结果追踪。新请求使用新 requestId/attemptId。旧结果不能自动成为候选或获得批准。此时界面持续提示“另有未确认远端请求”，两路上限只表示本地调度中的任务，不声称远端实际仍只有两路；自动批次绝不自行执行此例外。

离开页面、切换项目及返回均从持久任务与产物状态重建 UI。任务完成后自动刷新对应缩略图，但不抢走当前选中页、不清空其他页意见、不自动勾选人工审核项。

键盘可访问页码列表、历史版本和操作按钮。意见草稿按项目、页和所依据版本保存；发送失败保留文本。切换页或版本前完成本地草稿保存，保存失败明确提示且不静默离开。图片适应容器比例并可放大，不能通过裁切预览掩盖溢出。画廊使用小尺寸缩略图和懒加载，只解码有限数量完整图片。

## 5. 历史版本与 AI 修改

每页显示全部已知生成版本：版本号、生成时间、预览、审核状态，以及有记录时的提示词和意见。旧版本缺少生成依据时显示“旧版本未记录”，不反推或编造。只查看历史不会改变交付版本、审批或导出。

“基于此版本修改”固定 `parentVisualVersionId` 和图片哈希，将该历史图真实作为输入参考，并结合当前冻结文字、设计计划、模板和意见生成新的递增版本；不能只发送文字却宣称修改了选中的图片。历史原图永不覆盖。若当前 ImageGen 通道不支持经过校验的本地图片输入，此入口明确不可用，提供准确命名的“按当前内容重新生成”，不能静默降级。

图片处理使用既有宿主 ImageGen 能力和受控引用路径；具体输入协议须以本机可用协议验证，不根据未核实的字段编码。页面参考图和历史父图分别标记用途，不能混为事实来源或颜色模板。

### 5.1 交付选择和审批

- 查看版本 `inspectedVersionId`、当前交付版本 `activeVersionId`、历史审批分开存储。
- 从已批准页创建修改任务时，保留旧图和旧审批记录；该页进入“修订中”，暂停本次交付资格，当前导出/QA 指针失效但已有文件不删除。其他页批准保持有效。
- 新图完成成为待审核候选，原批准不自动转移。批准操作必须携带精确 versionId、图片哈希、内容/设计/配色哈希和人工检查结果。
- 想保留原图时选择“放弃本次修订，恢复原批准版本”；仅在所有影响该页的任务已明确终结、原文件和内容/设计/配色仍匹配时恢复原批准。否则进入重新审核。
- “采用其他历史版本”也需要显式人工确认。旧图若对应其他内容、设计或配色，不可直接批准为当前交付版本，只能作为修订参考。
- 内容或业务语义修改不走视觉意见绕过冻结，必须进入内容修订。全部页面当前交付版本都有效批准、无影响交付的未终结任务或未处理修订，才可转换及 QA。

当前阶段为 `visual_review` 时支持生成。已到 conversion / qa / completed 的项目可看历史；继续修改必须先显式“重新打开图片审核”，在转换/QA 执行中禁止操作，保留旧交付文件并使当前交付指针失效，再创建新的审核周期。

### 5.2 转换与 QA 使用同一交付快照

转换输入、导出 receipt、LibreOffice QA 对照图及最终交付索引必须共同绑定 `slideId → activeVersionId + imageHash` 和相应内容/设计/配色哈希，禁止通过历史数组最后一项选图。转换期间冻结本次交付快照；新审核周期不能覆盖旧交付路径。

保留独立 `PptxExporter` 接口和图片优先流程，但扩展其输入以接收已批准设计映射、演讲备注和转换布局计划。当前固定坐标回填不能直接用于新增的人物场景、流程节点或多区域布局。转换阶段应针对实际批准 PNG 定位文字区域与对象位置，形成与上屏对象 ID 对应的坐标计划；识别结果只用于定位，文字与数据仍取冻结规格，不能用 OCR 替换。

按已核对区域清除或重新生成无字背景，再叠加可编辑标题、正文、场景标签、表格、图表和基础形状；人物、照片、复杂场景插画允许保留图片。备注写入演讲者备注，不烘焙到页面。模型重建背景不能被当作已验证原样保留，必须做逐页视觉对照。若坐标缺失、文字区域未清理或当前能力不支持该布局，明确阻塞转换并保留批准 PNG，不把一张整页图包装成“可编辑完成”。自动修复上限沿用两轮，剩余问题写入 QA 报告。

## 6. 队列、持久化和并发一致性

### 6.1 任务真源

SQLite 保存批次、单页 Job、每次 attempt、派发意图、请求快照、提供方身份、暂存结果与提交回执。内存注册表只负责订阅/调度，不再作为真源。队列保存小型元数据，PNG 不以 base64 长期放在队列内存中。

Job 的目标至少包含 projectId、slideId、requestId、attemptId、冻结 spec 与设计计划的版本/哈希、技能和配色版本/哈希、父版本及参考图哈希、意见快照。唯一约束阻止同页重复未终结任务。派发前先保存意图；threadId / turnId 一旦取得即持久化，不等最终回包才保存。

任务状态区分 queued、dispatching、running、result_ready、committing、succeeded、failed、cancel_requested、cancelled、outcome_unknown、abandoned_unresolved。最后一种仅代表用户明确放弃本地等待，不代表服务已停止。批次暂停是独立标志；页审核状态独立于 Job 状态。只有队列明确派发后才称“生成中”，只有文件和回执保存成功才称“生成完成”。

### 6.2 结果提交

允许两个长时间图片调用并行；同一项目的完成提交和审批通过短事务串行执行。不能用启动时旧的整份 pipeline 覆盖最新项目，也不能取消全局 CAS 校验来假装解决冲突。

步骤：可靠暂存结果 PNG 和哈希 → 加载最新 pipeline → 校验此 Job 的目标快照仍有效且未被取消/替代 → 基于最新状态应用该页事件 → 同一 SQLite 事务记录候选、receipt、Job 终态、pipeline 和审批资格变化。发生与本页无关的 revision 竞争时重新读取并重试短提交，最多三次；仍冲突则停在可恢复的保存失败状态，不能重新调用模型。

文件系统与数据库不承诺跨介质的一次物理原子事务。通过不可变文件先落盘、业务指针后提交，保证候选对业务原子可见；崩溃留下的暂存文件按 manifest/hash 恢复。requestId 的完成提交幂等：已提交则返回原 receipt，不追加第二个版本。迟到旧 attempt 只保留可核查结果，不能覆盖新的版本或审批。

不同页完成、同页修改、单页批准、重新打开、导出启动都必须走同一个冲突与资格检查边界。调度和图片会话所有权置于 Rust 监管的 Worker 服务，不依赖 React 页面、WebView 或前端 Promise 的存活；前端只派发短命令并订阅事件。Worker stdin 收到启动命令后登记并返回 Job，实际图片调用在独立异步任务运行，不能让顺序 RPC 循环等待整张图片。Rust 负责持久化和短事务边界；关闭或刷新 WebView 不取消任务。完整退出应用或 Worker 崩溃则按恢复规则处理，不能承诺仍在后台执行。退出前不强杀已存在的用户 Codex 客户端。

### 6.3 重启和未知结果

关闭应用、系统睡眠或合盖不能保证本地任务继续运行。重启先读取已有 receipt 和可靠暂存结果，能补交本地结果就补交；只有经过当前 App Server 能力验证后才只读核查可恢复会话。`turn/start` 已发出但身份未落盘、临时会话丢失等情况标记 outcome_unknown，不自动创建新请求。

网络中断、限流、取消申请、客户端超时均不等同远端任务已停止。未知状态不自动释放名额或重试出图；页面提供核查、明确放弃等待的说明及手动重试入口。自动网络重试仅限可证明未发送的操作或只读查询，不能假设模型请求天然幂等。

### 6.4 旧 pipeline 兼容

并行页面事件使用新的 v3 pipeline 语义和验证路径，不能塞进依赖串行顺序的 v1/v2 重放逻辑。旧项目首先经原验证器完整验证，保留不可变原始快照和哈希。兼容隔离选择独立 v3 数据库和独立项目目录：用户第一次启用批量/版本修订时，经明确提示创建 v3 工作副本，分配新 projectId，所有文件与索引使用新路径；旧项目保持原样，不原地改为 v3。运行中或远端状态不明的项目不能升级。应用启动时识别新旧存储并用来源关联显示，避免把副本误认为无关项目。

v3 明确保存逐页当前版本及有效审批关系，重放不再在第一个无图页停止。纯格式升级不改变内容：历史审批以 `originApprovalRef` 指向原始有效记录，由迁移回执绑定新旧项目、版本、图片/内容/配色哈希，不创建冒名的新批准。迁移不重造历史、不补批准、不要求有图页连续；没有来源记录的旧图仍可查看，但按既有来源/配色核验规则决定能否交付。迁移失败不发布半成品副本，旧项目不受影响。

新旧应用不共享 v3 可写文件，旧二进制只能继续看到旧项目；不能声称新版能给已发布旧二进制补上“不兼容”提示。新版对未来未知 schema 显式拒绝写入。恢复旧应用意味着使用原项目，不是将 v3 数据降级覆盖。此处纯格式升级可以保留经核验的批准；第 7.1 节内容修订改变了内容意图，必须重新审核，两者不可混同。

## 7. 当前北苑项目与参考图

### 7.1 已冻结长正文的处理

新技能默认用于新项目或尚未冻结的草稿，不悄悄改变当前北苑项目已批准的内容。给现有项目提供“按售前结构创建内容修订副本”：新建独立 projectId，并用伴随 lineage 记录来源项目、版本及哈希。原项目、图片、审批和交付文件保持原样。

副本复用通过哈希验证的材料和分析快照，复制项目说明、配色和参考绑定作为新版本；原冻结大纲仅作为新大纲草稿和对照，不继承批准。新大纲再次确认后，按新技能生成和审核细化，再生成样页及批量出图。复用素材不代表重新运行材料分析；材料变更时才走对应重新分析流程。副本创建须先完整准备文件与索引再发布，失败不留下看似正常的半个项目。

副本入口明确告知需重新审核大纲、细化及新图片。用户可选择不修订，继续原流程；不能把旧正文原样冻结又承诺新技能必然消除文字堆叠。

### 7.2 北苑效果图用于驾驶舱页

将用户提供的北苑建筑效果图通过受控文件导入流程复制为不可变项目资产，绑定用户指定的运营驾驶舱页；若页名或对应关系不唯一，先让用户选择目标页。不得仅把图片留在临时剪贴板路径，也不得复制到所有页面。

用途标记为“项目建筑形态/场景参考”，不声称是已建成实景、现有系统截图或已部署功能。保留可见来源水印，备注其性质；图片中的文本不是执行指令。模板决定配色，该图决定项目场景参考，两者职责分开。绑定或变更影响已批准页面时创建显式修订，不改旧版本依据。

## 9. 验收标准

1. 大纲、细化和图片的实际请求均能核对技能版本、页面类型、模板与设计快照；缺少必需设计计划不能冒充新技能生成。
2. 建设目标、架构、场景三类样页人工查看：核心信息明确、层级清晰、没有正文堆叠；架构业务层和后续模块映射一致，人物动作、系统响应和流程连线能够说明实际使用。自动规则通过不等于美观验收通过。
3. 模拟五页按乱序完成，正常及自动恢复路径全应用最多两个派发中/运行中/状态未确认的 attempt，同页不重复；可审核已完成页且不影响其他页生成。用户显式放弃未知请求的例外另测：风险确认、新请求 ID、迟到结果隔离及远端未知提示，不用该例外宣称真实远端仍受两路硬上限约束。
4. 离开/返回页面、刷新、重启恢复，队列和意见草稿不丢失；未知远端结果不自动重发。派发前后、回包暂存后、数据库提交前后的崩溃点分别覆盖。
5. 两页结果与另一页批准交错提交，不覆盖对方；receipt 重复回放不新增版本；保存失败重试不新增模型调用。
6. 从历史 v1 提意见得到新 vN，父图真实入参且 v1 文件不变；预览历史不改变交付，旧图缺失/旧内容不匹配时不可误批准。
7. 每页当前交付版本、内容、设计、配色均有精确有效批准，且无未处理修订/任务才能进入转换。已有导出文件永不被版本查看或新候选覆盖删除。
8. v1/v2 原件与 v3 升级副本的原图、审批来源、哈希不丢失；失败不污染旧项目；旧应用操作原件不能更改 v3 数据或图像；严格拒绝未经许可的字段和工作区外/符号链接写入。
9. 单项目两路生成下重新记录新增内存峰值，目标不超过 4GB；长画廊不一次性解码所有历史原图。记录真实服务的并发/限流表现，不用模拟测试宣称服务能力已验证。
10. 真实出图、可编辑导出及 LibreOffice 回归通过，仍保证批准文字保真、无重叠烘焙文字；检查配置与网络调用不存在新增收费 API 路径。Keynote 人工检查按可用环境单独记录。
11. 已生成 v3 图片后选择采用历史 v1，实际 PPTX、receipt 和 QA 都使用所选 v1；独立检查场景标签可编辑、备注没有出现在 PNG、设计映射失效时不能批准或静默按固定坐标导出。

## 10. 设计确认点

默认方案为：全应用两路生成；逐页独立审核；历史图不可变，修改产生新版本；现有已冻结内容需新建修订副本并重新审核；企业模板优先控制配色，场景图提供真实项目参考。书面设计确认后再编写实施计划、测试用例和代码，不在此阶段改动客户项目或运行新的批量生成。
